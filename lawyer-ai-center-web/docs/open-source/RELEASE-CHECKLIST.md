# 首次开源发布检查清单

本清单面向维护者。请在真实完成后填写 `PASS / FAIL / BLOCKED / NOT_RUN / NOT_APPLICABLE`；`NOT_RUN` 必须注明“未验证”。README、致谢和免责声明不能替代实际检查。

## 1. 权利与上游

- [ ] 确认公司有权许可本项目新增代码；涉及员工、外包、客户交付或联合开发的，核对合同归属与开源授权。
- [ ] 保留 `ruoyi-ai/`、`ruoyi-web/`、`ruoyi-admin/` 的原始许可证和文件头，不删除原作者、版权及必要 NOTICE。
- [ ] 逐项核对 [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md) 中直接上游及本次实际使用版本；尚未确定的来源不得当作已完成核验。
- [ ] 根据两个 pnpm 锁文件和 Maven 实际依赖树生成版本化依赖清单/SBOM，检查传递依赖、许可证兼容性与分发义务。当前来源表不是完整 SBOM。
- [ ] 核查 LOGO、字体、图标、截图、PDF、合同/文书模板、数据库/案例/法规内容、样例文件和模型权重的授权。来源可访问不等于可任意再分发。
- [ ] 不使用“官方分支”“上游合作”“零侵权”“零风险”“法律效果保证”等未经证实的表述。

## 2. 秘密与资料：当前文件和 Git 历史分别检查

- [ ] 查看拟发布列表：`git ls-files --cached --others --exclude-standard`。不要直接对整个工作目录执行盲目的 `git add .`。
- [ ] 确认真实 `.env`、`application-dev.yml`、数据库副本、上传文件、日志、研究资料、临时目录和本地密码 SQL 未被纳入；新 `.gitignore` 对已跟踪文件和历史提交不生效。
- [ ] 使用维护中的秘密扫描器扫描当前工作树及**完整拟公开 Git 历史**；人工复核误报，保存工具版本、范围和脱敏结果。不得仅搜索当前 README 或 SQL 就宣称无秘密。
- [ ] 检查各脚本、测试夹具、工作流、Docker 配置和文档中的 API Key、云密钥、JWT/RSA、数据库/Redis/SMTP/OSS 凭据与可识别的真实数据。
- [ ] 已经泄露的真实凭据应先撤销/轮换，再处理历史。重写历史、强推或更改远端可见性需另行授权和协调；本次不执行这些动作。
- [ ] 当前工作区有与本次任务无关的在途修改；发布前逐项选择变更，防止将未验收业务或内部文档一起公开。

可使用 [Gitleaks 官方项目](https://github.com/gitleaks/gitleaks)等工具按其当前文档运行；本记录不宣称已经执行该工具或覆盖全部秘密模式。

## 3. 数据库与初次安装

- [ ] 运行 `python scripts/open_source/build_init_sql.py --check`，确保生成 SQL 与基线及迁移一致，新增迁移未遗漏。
- [ ] 在**独立空 MySQL 8.0.30+ 实例**中测试完整导入；确认两个库均创建、命令退出 0、有完成标记，且不是只执行了前几行。
- [ ] 验证公开原版管理员锁定；本地配置副本使用安装者自选密码，四个助手和示例模型停用，注册关闭，业务表为空。
- [ ] 验证重复导入会在首个已存在数据库处停止，不改变已有记录；明确脚本遇错后 DDL 可能已部分提交，禁止 `--force`。
- [ ] 对照当前实体与 SQL 使用点检查表和字段；默认用户不得获得系统管理员、模板写入等越权能力。
- [ ] 已有库使用增量迁移，先备份并验证恢复，不用全量 SQL 覆盖生产库。不把初始化脚本当作线上数据迁移工具。

可复现隔离测试工具为 [`verify_init_sql.py`](../../scripts/open_source/verify_init_sql.py)。它只允许项目 `tmp/` 下的数据目录、回环地址和非 3306 端口，核对服务实际目录后才创建随机命名的测试库。

## 4. 配置、部署与验收

- [ ] 从公开样例创建私有环境配置。确认前端变量均视为公开；不会将服务端秘密打包进浏览器。
- [ ] 在干净检出中验证 README 的两个 pnpm 固定版本、锁文件安装、后端打包和真实服务启动；构建成功不等于业务通过。
- [ ] 配置应用专用数据库账户、Redis、HTTPS、来源白名单、存储桶和模型；监控、调度、第三方登录、MCP 等按需启用并独立验收。
- [ ] 使用合成材料走通登录、权限、案件、上传、解析、来源复核、文书与导出，并验证无权限、解析失败、外发策略拒绝和服务超时。
- [ ] 运行与实际改动相称的后端、前端、安全及可用性检查；结果如实记录。不把本次 SQL 验证推广为整站验收。
- [ ] 确认未采用上游预构建镜像冒充与律行发行版。若未来发布镜像、压缩包或安装包，同步携带相应许可证、NOTICE 与第三方声明。
- [ ] 完成数据备份/恢复、日志脱敏、账号关闭、权限回收及服务不可用时的运维流程。

## 5. 仓库发布资料

- [ ] 核对中英文 README、公司 LOGO、电话、邮箱、官网与公众号入口；检查相对链接和浅/深色显示。
- [ ] 添加自己的仓库简介和主题词，例如 `legaltech`、`lawyer`、`ai`、`vue3`、`spring-boot`；官网字段可指向[前进公司](https://www.qjsec.com)，不虚构 Star、客户量或效果数据。
- [ ] 设置版本标签与变更说明，写明数据库版本、升级边界、已知限制和验证环境。
- [ ] 明确支持入口为当前仓库和公司邮箱，说明上游独立性，不将本项目支持责任转移给原作者。
- [ ] 最后复核实际发布内容与检查记录。公开仓库、推送、标签、Release、镜像发布等外部动作本次未执行，执行前另行确认具体范围。
